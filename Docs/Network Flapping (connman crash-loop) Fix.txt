Network Flapping / "No Network" Fix (connman crash-loop)
===========================================================

Symptom
-------
- WiFi and/or Ethernet is flaky or drops out entirely while booted with
  the MockbaMod SD card.
- The WiFi and Ethernet settings menus on the Force's own screen misbehave
  (grey out, don't update, look stuck).
- Consistently fine when booted into stock Akai OS (no SD card).
- `dmesg` shows eth0 (or the wlan interface) repeatedly cycling
  Link Up / Link Down, sometimes dozens of times in a few minutes:

    rk_gmac-dwmac ff290000.ethernet eth0: Link is Up - 1Gbps/Full ...
    rk_gmac-dwmac ff290000.ethernet eth0: Link is Down
    rk_gmac-dwmac ff290000.ethernet eth0: PHY [stmmac-0:01] driver [RTL8211E Gigabit Ethernet] (irq=68)
    ... repeats continuously ...

Root cause
----------
`systemctl status connman.service` shows it stuck in a crash-restart
loop ("activating (auto-restart)", restart counter climbing every
~1 second). `journalctl -u connman.service` shows the actual crash:

    Setting hostname to force
    eth0 {add} address 192.168.1.x/24 label eth0 family 2
    Failed to find URL:http://ipv4.connman.inmusicbrands.com/
    Aborting (signal 6) [/usr/sbin/connmand]

This InMusic/Akai build of `connmand` performs an online-connectivity
check against a vendor URL (`OnlineCheckIPv4URL` in
`/etc/connman/main.conf`) and **aborts the whole daemon (SIGABRT) if
that check fails or is slow**, instead of just logging it and retrying.
DNS resolution and basic routing are not the problem — the check itself
(an HTTP fetch to that URL) is what's failing/timing out.

Normally a single connman crash wouldn't be a big deal — systemd's
default restart-limit (5 restarts / 10s) would let it fail a handful of
times and then settle into a stopped "failed" state. But this device has
a pre-existing (not MockbaMod-authored — not present anywhere in this
repo, confirmed by grep) drop-in at
`/etc/systemd/system/connman.service.d/override.conf`:

    [Unit]
    StartLimitIntervalSec=0

    [Service]
    Restart=always
    RestartSec=1
    StartLimitBurst=0

`StartLimitBurst=0` disables systemd's crash-loop protection entirely.
Combined with the online-check crash, connman restarts every ~1 second,
forever — and every restart brings the managed interface(s) down and
back up, which is the flapping you see in `dmesg` and the misbehaving
network menus (both WiFi and Ethernet settings UI are driven by connman
over D-Bus, so a connman that never stays up for more than a second
breaks both, not just WiFi).

Why it's fine on stock OS: unclear whether stock ships the same
override.conf. Either way, this is a real crash bug in connman itself
(failing a reachability check should never abort the process) — the
override.conf just turns an isolated crash into permanent flapping
instead of a clean, bounded failure.

Update (2026-09-22 evening): a second, different connman crash
------------------------------------------------------------------
The online-check fix below stops *that* crash, but connman turns out to
have at least one more SIGABRT trigger, unrelated to the online check.
Caught live with the online check already disabled:

    wlan0 {newlink} index 4 operstate 6 <UP>
    Setting hostname to force
    Online check disabled. Default service remains in READY state.
    Aborting (signal 6) [/usr/sbin/connmand]

This happens right as eth0 and wlan0 both reach "ready" around the same
time — looks like a race in connman's default-service-selection logic
when two technologies come up close together, not anything the online
check controls. We don't have connman's source for this InMusic/Akai
build, so it can't be patched directly.

**This changes the right answer for the restart-limit question below.**
A first pass at this fix restored systemd's default restart limit (5
restarts / 10s) as "defense in depth." That was wrong for this daemon:
since it has at least one more crash trigger we can't eliminate, hitting
that limit means connman gives up permanently and *stays down* until a
human notices and restarts the Force — which is worse than the flapping
it was meant to prevent, and matches reports of needing "multiple
restarts" to get network back. For a vendor daemon with sporadic
unpatchable crashes, unlimited auto-restart (self-heals within a second
or two, worst case a brief flap) beats a bounded retry that can end in
permanent failure. Keep `StartLimitBurst=0`.

Fix
---
Two independent changes, both required:

1. **Stop the known crash** — disable connman's online-connectivity
   check entirely (`/etc/connman/main.conf`):

       [General]
       OnlineCheckIPv4URL = http://ipv4.connman.inmusicbrands.com/
       EnableOnlineCheck = false

   This eliminates the online-check abort specifically. It does not
   eliminate the second (wlan0-race) crash above — nothing currently
   does, short of an upstream connman fix.

2. **Guarantee unlimited auto-restart**, so whatever crashes connman
   (known or not), it keeps retrying instead of ever going permanently
   `failed` — (re)write `/etc/systemd/system/connman.service.d/override.conf`:

       [Unit]
       StartLimitIntervalSec=0

       [Service]
       Restart=always
       RestartSec=1
       StartLimitBurst=0

   `StartLimitBurst=0` disables systemd's crash-loop protection. That's
   intentional here, not a bug to "fix" — see the update above. Yes,
   this does mean a crash still visibly flaps the interface for ~1
   second; it just guarantees that flap is temporary instead of a dead
   network requiring a manual restart.

Both files live on the device's real eMMC `/etc`, **not** on the
MockbaMod SD card / OverlayFS, so this fix is not part of the addon
tree and isn't something `manage.sh ENABLE/DISABLE` touches. Confirmed
2026-09-22 that it survives a `emmcRepair` addon run (`main.conf` and
the rewritten `override.conf` were both untouched by the repair). It
will NOT survive a full Akai firmware reflash — reapply after any
firmware update if the flakiness comes back.

Applying it
-----------
Run `scripts/fix-connman-crashloop.sh` (in this repo) against the
Force over SSH — see `Docs/SSH-SFTP Instructions.txt` for connecting.
It's idempotent: safe to run again after a firmware update or if you're
just not sure whether the fix is already in place.

    python3 tmp_ssh.py <force-ip> "$(cat scripts/fix-connman-crashloop.sh)"

or copy it to the device and run it directly over SSH as root.

Verifying it worked
--------------------
    systemctl show connman.service -p MainPID,ActiveState,SubState,NRestarts
    # ActiveState=active, SubState=running.
    # NRestarts may occasionally tick up (the wlan0-race crash above can
    # still happen) — that's expected and fine as long as ActiveState
    # stays "active" a few seconds later. What matters is it never sits
    # in "activating (auto-restart)" for more than ~1-2 restarts in a row,
    # and never goes to "failed".

    dmesg | grep -c 'eth0: Link is Down'
    # a rare single flap (one crash, self-healed) is normal now; dozens
    # in a short window is not — that'd mean a new persistent trigger.

    ping -c 10 <force-ip>
    # 0% packet loss, stable low-ms latency

Update (2026-10-08): WiFi dies for good after a crash — LoadPin + /usr overlay
-------------------------------------------------------------------------------
This one IS MockbaMod-specific. The kernel enforces LoadPin: firmware and
kernel modules may only be loaded from the pinned read-only root fs
(mmcblk0p6). MockbaMod's overlay.sh mounts an OverlayFS over /usr, so
after boot /usr/lib/firmware lives on the overlay, not the root fs.

The WiFi chip (BCM4339 over SDIO) loads its firmware once at ~4s, before
the overlay exists, so it works at first. But during the boot-time
connman crash-restart churn the chip hung ("brcmf_fil_cmd_data: bus is
down"), the SDIO card was removed/re-probed, and the firmware reload was
refused:

    LoadPin: firmware denied obj="/usr/lib/firmware/cypress/cyfmac4339-sdio.bin"
    brcmfmac mmc2:0001:1: Direct firmware load for brcm/brcmfmac4339-sdio.bin failed with error -1

wlan0 then simply doesn't exist until a reboot. Without the card there's
no overlay, so the same chip reset recovers on its own.

Fix (in MockbaMod/overlay.sh): bind-mount the stock root's usr/lib/firmware
and usr/lib/modules back over the overlay (via a bind of / at
/run/stockroot), so those reads come from the pinned root fs again.
Verified live: after the bind, re-binding the SDIO device to brcmfmac
loaded firmware and brought wlan0 back without a reboot.

Manual recovery without rebooting (if WiFi has vanished):
    mkdir -p /run/stockroot; mount --bind / /run/stockroot
    mount --bind /run/stockroot/usr/lib/firmware /usr/lib/firmware
    for n in 1 2 3; do echo mmc2:0001:$n > /sys/bus/sdio/drivers/brcmfmac/bind; done

Still open: connman itself still aborts ~5 times during boot and once
right after systemd-timesyncd steps the clock forward (the RTC has no
valid time, so every boot starts hours behind; ~18s after the NTP step
connman drops its DHCP address and aborts). The first boot-time abort
happens before MockbaMod's boot scripts run. connman's stderr is sent to
/dev/null by its unit, so the abort reason was never visible; a drop-in
/etc/systemd/system/connman.service.d/zz-capture-stderr.conf now sets
StandardError=journal. After the next crash:
    journalctl -u connman.service -b | grep -B5 Aborting
